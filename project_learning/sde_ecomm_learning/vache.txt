2. Why separate PostgreSQL and Snowflake?
This is an important interview question.
PostgreSQL = OLTP
It handles:
•	Users
•	Books
•	Categories
•	Orders
•	Order items
•	Payments
•	User events
For example:
orders
---------
id
user_id
total_amount
status
created_at
This database is optimized for transactional operations.
When a customer purchases a book:
React
  ↓
POST /api/orders/
  ↓
Django
  ↓
PostgreSQL
We need ACID transactions and immediate consistency.
Snowflake = OLAP
I don't make Snowflake the transactional database.
Instead:
PostgreSQL
    ↓
Python/Airflow ingestion
    ↓
Snowflake RAW
    ↓
STAGING
    ↓
DIM/FACT
    ↓
MART
This allows analytical queries such as:
SELECT
    category,
    SUM(revenue)
FROM mart_book_sales
GROUP BY category;
without putting analytical workload on the production Django database.

3. Where do PDFs and images go?
This was one of the important architecture decisions.
Cloudinary

   ↓
Cloudinary

Book Cover
   ↓
Cloudinary
PostgreSQL stores only the reference:
Book
----------------
id
title
author
price
file_url
cover_url
category_id
So we're not putting large binary objects into our transactional database.
The response becomes:
{
    "id": 1,
    "title": "Python Interview Kit",
    "price": "500.00",
    "file": "https://cloudinary/.../python.pdf",
    "cover": "https://cloudinary/.../python.jpg"
}
This also solved the Render filesystem problem.
Render's free service filesystem is ephemeral, so storing uploaded files under Django's /media directory isn't durable.

4. What exactly happened with our image bug?
This is actually a great interview debugging story.
Initially:
Django Admin
     ↓
Book exists
     ↓
cover exists
     ↓
API
     ↓
React
     ↓
❌ image not displayed
We didn't immediately assume the frontend was broken.
We debugged layer by layer.
Step 1 — Check database
The Book object contained:
b.cover
# books/covers/dj_mfpnjiM.png
And:
b.cover.url
# /media/books/covers/dj_mfpnjiM.png
So database/file metadata existed.
Step 2 — Check actual filesystem
Inside Docker:
/app/media/books/covers/dj_mfpnjiM.png
existed.
Therefore:
Database       ✅
Django storage ✅
Physical file  ✅
Step 3 — Check serializer
We discovered the serializer didn't expose cover or file.
Original:
fields = [
    "id",
    "title",
    "author",
    "price",
    "category",
    "description",
    "is_active",
    "created_at",
    "updated_at",
]
So even though the model contained the file, the API didn't return it.
We changed it to:
fields = [
    "id",
    "title",
    "author",
    "price",
    "category",
    "description",
    "file",
    "cover",
    "is_active",
    "created_at",
    "updated_at",
]
No migration was required because this was only a serializer change.

5. Then we discovered another issue: API response structure
The backend returned:
{
    "success": true,
    "message": "Books fetched",
    "data": {
        "count": 2,
        "results": [...]
    }
}
But frontend was doing:
response.data?.results
That looked for:
data.results
at the Axios response level.
The actual structure was:
response.data
    ↓
{
    success,
    message,
    data
}
    ↓
data.results
So the fix was:
const body = response.data;

return body?.data?.results || body?.results || [];
This is a classic API contract mismatch.
In an interview:
“I traced the issue across the database, serializer, API contract and frontend instead of assuming it was a UI issue.”
That's a strong senior-level answer.

The serializer was fixed.
The API was returning the URL.

Therefore:
Serializer       ✅

React            ✅
File serving     ❌
Final architecture
Move actual files to:

and PostgreSQL keeps the URLs.

7. Where Redis fits
Redis is not our database.
It's a cache.
For example:
GET /api/books/books/
          │
          ▼
       Redis
       /     \
     HIT     MISS
      │        │
      ▼        ▼
   Return   PostgreSQL
              │
              ▼
            Redis
Our cache key was based on the request:
cache_key = f"books_list_{request.get_full_path()}"
And TTL:
timeout=60 * 3
So approximately 3 minutes.
Why?
Book listings are read-heavy.
Instead of:
1000 requests
→ PostgreSQL 1000 times
we can have:
1 request → PostgreSQL
999 requests → Redis
This reduces database load and latency.
________________________________________
8. Why Redis cannot be the source of truth
Suppose Redis crashes.
We should still have:
PostgreSQL
   ↓
Books available
Redis can disappear and be rebuilt.
Therefore:
PostgreSQL is the source of truth; Redis is a performance optimization.
This is a very important interview statement.

9. Another issue: stale Redis cache
We noticed something important.
If an administrator changes a book directly through Django Admin:
Admin
 ↓
PostgreSQL updated
but Redis may still contain the old book list.
Therefore the API can temporarily return stale data.
Our ViewSet explicitly clears cache when modifications happen through the API:
def perform_create(self, serializer):
    serializer.save()
    cache.clear()
Same for update/delete.
But Django Admin doesn't execute these ViewSet methods.
Senior-level improvement
I would eventually implement cache invalidation at the model/service layer or use Django signals/event-driven invalidation rather than relying only on ViewSet methods.
For example:
Book updated
    ↓
Domain/service layer
    ↓
DB commit
    ↓
Cache invalidation
Even better:
transaction.on_commit(...)
so cache invalidation happens only after the database transaction successfully commits.

10. Important Redis failure handling
Our code intentionally doesn't make Redis a hard dependency.
try:
    cached = cache.get(cache_key)
except Exception:
    logger.warning("Redis unavailable")
If Redis goes down:
Redis ❌
   ↓
PostgreSQL ✅
   ↓
API continues
That's called graceful degradation.
A cache outage should not take down the bookstore.
This is another strong senior interview point.

15. Why select_related('category')?
Our query uses:
Book.objects.filter(
    is_active=True,
    category__is_active=True
).select_related('category')
Because every book response contains category information.
Without select_related, serializers can cause additional queries:
Book query
+
category query
+
category query
+
category query
...
Potential N+1 problem.
With:
select_related('category')
Django can fetch the related FK through a SQL join.
So:
“I use select_related for the foreign-key relationship to reduce N+1 queries.”

31. Biggest interview lesson from the actual debugging
If interviewer asks:
“Tell me about a production issue you solved.”
Use this:
“We had a situation where books existed in PostgreSQL and Django Admin, but the React application wasn't displaying them. I debugged it layer by layer rather than assuming it was a frontend problem. First I verified the database record and physical media file, then inspected the serializer and found that file and cover weren't included in the API fields. After exposing them, I found a second issue where the frontend expected results at the wrong response level because our backend wrapped the response under data. Once that was fixed, the API returned the correct absolute URLs, but directly opening the media URL still returned 404 on Render. That identified the final architectural problem: Render's free filesystem is ephemeral. We therefore moved customer-facing PDFs and covers to object/file storage and kept only their URLs in PostgreSQL.”
That's an excellent senior debugging story because it demonstrates:
Root-cause analysis
      +
API design
      +
Django
      +
React
      +
PostgreSQL
      +
Redis
      +
Cloud deployment
      +
Architecture
